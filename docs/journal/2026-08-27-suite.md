# 27 août 2026, huitième partie — Monitorage du service IA (C20)

Branche : `feat/bloc2-monitorage-c20`, créée depuis `feat/bdd-postgresql-c4`.

## Pourquoi ce chantier avant l'API du service IA

C'est le seul chantier dont la valeur dépend du temps écoulé. Une suite de tests
écrite demain vaut autant qu'écrite ce soir ; un monitorage lancé ce soir
capture huit jours de traces avant la soutenance. L'ordre n'est pas une question
de difficulté.

## Ce qui a été fait

`apps/monitoring/` : cinq modules — journal, sondes, alertes, coûts, analyse.
Le paquet n'est pas une application Django et ne déclare aucun modèle : le
monitorage doit survivre à la panne qu'il observe.

L'instrumentation passe par le point d'accroche global de LangChain,
`register_configure_hook`, celui qu'utilise LangSmith. Une seule inscription
couvre tous les appels de modèles et toutes les recherches RAG, existants comme
à venir.

Le service tourne sur le port 8000, sonde branchée, et accumule des traces.

## Difficultés

**Deux rappels à brancher, pas un.** `ChatGroq` et `ChatOllama` passent par
`on_chat_model_start` et non par `on_llm_start`. N'avoir branché que le second
aurait laissé la totalité des appels du projet hors du monitorage — sans qu'un
seul message ne le signale. C'est le genre d'erreur qu'on ne découvre qu'en
vérifiant qu'une trace apparaît vraiment, pas en relisant le code.

**Le nom du modèle est rangé à quatre endroits différents.** `model_name` pour
Groq, `model` pour Ollama, dans les paramètres d'invocation ou dans les
arguments sérialisés selon le chemin. Chercher aux quatre coûte six lignes ; ne
chercher qu'au premier aurait produit un journal où la moitié des appels sont
attribués à un modèle « inconnu ».

**Mon propre outil d'analyse annonçait « 0 recherche RAG » à côté d'une latence
de recherche non nulle.** Le décompte ignorait les recherches en erreur.
Exactement l'écart que ce module existe pour ne pas produire — corrigé, avec un
commentaire qui dit pourquoi le décompte est séparé.

## Choix effectués

- **JSON Lines dans un fichier, jamais en base.** Écrire les traces dans
  PostgreSQL, c'est les perdre quand PostgreSQL tombe. Une ligne par événement
  et non un tableau JSON : un tableau doit être refermé pour être valide, et un
  processus tué rendrait illisibles toutes les traces antérieures à l'incident.
- **`O_APPEND` à chaque écriture.** Le noyau positionne et écrit en une
  opération : deux processus n'entrelacent pas leurs lignes.
- **Mesurer des effets et non des intentions.** Les fragments rendus et non le
  `k` demandé ; les jetons facturés et non une estimation tirée d'une longueur
  de texte ; `verifier()` qui rouvre le fichier au lieu de rapporter ce que le
  journal croit avoir écrit. C'est la leçon des quatre incidents de ces deux
  jours, tous du même motif.
- **Un coût inconnu vaut nul, pas zéro.** Zéro se confond avec un appel
  gratuit ; nul se voit. Les tarifs portent un drapeau `a_verifier` que chaque
  événement transporte.
- **L'alerte s'écrit dans le journal, sans service externe.** Un service de
  notification tombe souvent en même temps que ce qu'il surveille.
- **Un plancher d'appels avant d'évaluer un taux.** Sans lui, le premier appel
  raté de la journée produirait un taux de 100 pour cent.
- **Un silence par nature d'alerte, pas global.** Une alerte de latence ne doit
  pas masquer une montée du taux d'erreur pendant dix minutes.
- **Ni prompt ni requête consignés, seulement leur longueur.** Un prompt peut
  contenir du code d'apprenant. Même règle de minimisation que pour le corpus.
- **Un décorateur plutôt qu'un bloc `with`** pour nommer l'agent : réindenter
  des méthodes de cinquante lignes dans du code qui fonctionne, à dix jours du
  rendu, ne valait pas le gain.

## Vérifications

| Contrôle | Résultat |
|---|---|
| Appel Groq réel | tracé — 3,64 s, 86 jetons entrée, 50 sortie, coût estimé |
| Modèle inexistant | tracé — `NotFoundError`, code de retour **404** |
| Erreur RAG | tracée — trace tronquée par le début, cause conservée |
| Alerte de taux sous le plancher | aucune |
| Alerte de taux au plancher | déclenchée |
| Alerte de latence | déclenchée une fois |
| Dix alertes redondantes | absorbées par le silence, 2 lignes au total |
| `verifier()` | relit le fichier et compte les lignes réellement présentes |
| Rapport d'analyse | agents, modèles, codes de retour, latences en médiane et d9 |
| Service en fonctionnement | port 8000, événement de démarrage écrit |
